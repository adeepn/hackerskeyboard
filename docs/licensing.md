# Лицензирование и provenance

> Это инженерная политика соблюдения лицензии, а не юридическая консультация.
> Для спорного происхождения кода, смены лицензии или коммерческого релиза нужно
> получить профессиональную юридическую оценку.

## Лицензия проекта

В корне находится полный текст Apache License 2.0 в файле `LICENSE`. Его нельзя
сокращать, переписывать или заменять переводом. Перевод может существовать только
как справочный документ; английский текст остаётся нормативным.

Проект содержит код с notices следующих правообладателей, среди прочих:

- The Android Open Source Project;
- Google Inc.;
- Darren Salt;
- другие авторы отдельных раскладок и вкладов, которые предстоит выявить полной
  инвентаризацией истории и файлов.

Это означает, что нельзя заменить исходные заголовки общим копирайтом нового
форка. Первичные notices продолжают относиться к исходному коду, а новые
изменения не делают первоначального автора автором этих изменений.

## Что требует Apache-2.0 при распространении производной работы

Практически важные требования раздела 4:

1. получателю предоставляется копия Apache License 2.0;
2. изменённые файлы несут заметное указание, что они были изменены;
3. в source distribution сохраняются относящиеся к работе copyright, patent,
   trademark и attribution notices;
4. если исходная работа включает `NOTICE`, относящиеся notices из него
   воспроизводятся в допустимой форме;
5. дополнительные attribution notices не должны изменять условия лицензии.

Официальный текст:
[Apache License 2.0](https://www.apache.org/licenses/LICENSE-2.0.html).
Практические пояснения:
[Apache Licensing FAQ](https://www.apache.org/foundation/license-faq.html).

## Правила изменения существующих файлов

- Сохранять исходный copyright и Apache-2.0 header дословно, кроме безопасной
  нормализации URL `http` → `https` при отдельной механической правке.
- Не заменять `The Android Open Source Project`, `Google Inc.`, имя автора или
  годы на имя нашей организации/форка.
- При материальном изменении добавить рядом с header короткое заметное указание,
  например:

```text
Modified for Hacker's Keyboard v2; see the repository history for details.
```

  Формат комментария подбирается под Java/Kotlin/C++/XML. Указание не должно
  утверждать передачу copyright и не должно приписывать изменения старому
  автору.
- Не добавлять modification notice за чистое перемещение без изменения
  содержимого, если история и notice сохраняются; неоднозначный случай
  фиксировать в PR.
- При разделении или объединении файлов переносить все применимые notices, а не
  только один выбранный header.

Git history полезна для provenance, но сама по себе не заменяет требование о
заметном указании в распространяемом изменённом файле.

## Новые файлы

Новый production source должен иметь Apache-2.0 identifier/header. Короткий
вариант допустим, когда он соответствует политике проекта:

```text
SPDX-License-Identifier: Apache-2.0
```

Copyright line добавляется только с реальным правообладателем и после решения
владельца проекта. Нельзя автоматически указывать автора исходного AOSP файла,
Klaus Weidner, Codex, Claude или другого инструмента как правообладателя нового
файла.

Для генерируемого кода должно быть ясно, какой source/template определяет его
лицензию и должен ли header появляться в generated output.

## Форки, upstream и сторонние snippets

До переноса кода в PR указываются:

- source repository URL;
- exact commit/PR и конкретные файлы/hunks;
- лицензия source repository на этом commit;
- существующие file headers и `NOTICE`;
- авторство/attribution, которое необходимо сохранить;
- описание адаптации и наши modification notices.

Совпадающая Apache-2.0 лицензия не разрешает удалять исходные notices. Если
лицензия отсутствует, неоднозначна или несовместима, код не копируется; идею
можно независимо реализовать по публичному описанию без заимствования текста.

AI-generated ZIP из issue, произвольный gist, Stack Overflow answer или файл без
ясной лицензии считается неизвестным источником. Его нельзя помещать в рабочий
tree до provenance review.

## NOTICE и third-party компоненты

На момент первичного аудита в repository отсутствует `NOTICE`, хотя `LICENSE`
есть. Нельзя автоматически утверждать, что этого достаточно или что произвольный
NOTICE обязателен: сначала S1.22 должен определить provenance исходного проекта,
ресурсов и бинарников.

Особенно проверить:

- `app/libs/voiceimeutils.jar` 2011 года;
- native dictionary sources и формат/данные словаря;
- `app/src/main/res/raw/main.dict`;
- изображения, NinePatch, звуки и прочие AOSP resources;
- новые Gradle plugins/actions/dependencies;
- раскладки и compose sequences из PR/форков.

После inventory создаётся минимальный корректный `NOTICE` и/или файл
third-party notices, содержащий только относящиеся attribution notices. `NOTICE`
не используется для добавления новых лицензионных ограничений.

## Релизы

Source archive, APK/AAB distribution page и иные поставляемые пакеты должны:

- сохранять root `LICENSE` в source distribution;
- предоставлять пользователю доступ к Apache-2.0 license и применимому `NOTICE`;
- включать third-party notices/licenses, требуемые bundled dependencies;
- не удалять notices из исходников;
- маркировать продукт как модифицированную/производную версию, не создавая
  впечатления официального релиза AOSP, Google или первоначального автора;
- сохранять attribution переносимых fork contributions.

Состав APK/AAB и release archive проверяется автоматическим license job после
реализации S1.24.

## Checklist PR

- [ ] Все существующие notices сохранены.
- [ ] Материально изменённые legacy files имеют modification notice.
- [ ] Новые files имеют корректный Apache-2.0 identifier/header.
- [ ] Внешний код имеет точный provenance и совместимую лицензию.
- [ ] Изменения `LICENSE` отсутствуют либо имеют отдельное юридическое решение.
- [ ] `NOTICE`/third-party attribution обновлены, если применимо.
- [ ] Release packaging не теряет license/notice information.
- [ ] PR не приписывает AI-инструменту copyright или авторство.
